# Тренажёр оператора ДДС (АРМ-112) — архитектура решения

> Задача 9, Департамент обороны и ЧС. Изолированный контур, офлайн, без внешних сетей.
> Целевое железо, от которого пляшем: **Intel Core i5 8–10 поколения (4C/8T, AVX2, без AVX-512, без SHA-NI), 8–16 ГБ RAM, SSD, без GPU.**
> Стек: **C11 (ядро) + Python 3.11 (прикладной слой)**.

---

## 0. Зафиксированные решения

| Вопрос | Решение |
|---|---|
| Предметная модель | Восстановлена из первичных документов заказчика (классификатор v.046.24, памятка ДДС, билеты, инструкция, снимки стенда, ответы заказчика), а не реконструирована — см. §10 |
| Роль ДДС | По ответу заказчика: только статусы и комментарии, бригада выбирается вручную, связь по IP-телефону, **единый алгоритм для всех служб** — см. §10.7 |
| Маршрутизация | Три слоя: тип и признаки → район обслуживания → подчинённость объекта; первый слой проверен на стенде — 14 из 16 точно, 0 ошибок — см. §10.8 |
| Модель занятия | **Локальное лобби с авторитарным сервером**: преподаватель — владелец, роли участников = ДДС служб, пустые слоты закрывают боты — см. §18 |
| Топология | **Учебный класс = вычислительный кластер**: тяжёлое считается на простаивающих АРМ, решения об оценке — только на сервере |
| Голосовой канал | WS-audio (PCM16 16 кГц) в браузере + собственный **SIP/RTP мост `rtpd` на C** для реальных IP-телефонов |
| ИИ-генерация | **llama.cpp** + GBNF-грамматика + комбинаторный движок, распределённо по узлам класса. В поставке две модели (1.5B и 7–8B), размер выбирается по профилю узла |
| ИИ-оценка | **Чистый C, без нейросетей**: морфология, факты, рубрики, GBDT |
| ASR | **whisper.cpp `base`, по одному потоку на АРМ**, слот-чек-лист вместо транскрипта; в режиме аттестации — на сервере |
| Горизонт | 1–2 недели |
| Поставка | Две независимые сборки: портативный бандл Windows и пакет/Docker для Ubuntu, отдельные пайплайны CI |
| СУБД | PostgreSQL 14 (совместимость с 12+ по ТЗ) |

## 1. Ключевой архитектурный принцип: асимметрия генерации и оценки

Всё решение строится на одном наблюдении: **генерация и оценка имеют несовместимые бюджеты.**

| | Генерация | Оценка |
|---|---|---|
| Когда происходит | до занятия, преподавателем | внутри занятия, 20+ параллельно |
| Допустимое время | 10–60 с | ≤200 мс (норматив ТЗ — 2000 мс) |
| Частота | десятки раз в день | тысячи раз |
| Реализация | LLM в отдельном процессе, завершается после работы | нативный C, детерминированный |

Следствия:

1. **LLM никогда не сосуществует с активным занятием** — его 1.3 ГБ не входят в пиковый бюджет памяти.
2. **Оценка объяснима**. Преподаватель видит, *почему* снижен балл: какой обязательный факт не покрыт, какое слово с ошибкой и какие кандидаты замены, где нарушено согласование, какое поле просрочено. Это принципиальное преимущество перед «нейросеть так решила» и прямое попадание в критерий «скорость работы решения».
3. **Оценка не деградирует под нагрузкой.** 20 сессий — это 20 × 5 мс работы CPU в секунду, то есть ~10% одного ядра.

## 2. Учебный класс как вычислительный кластер

Второй несущий принцип. В классе стоят 20+ АРМ, каждый — i5 (4C/8T) с 8–16 ГБ,
и во время подготовки занятия они **простаивают**. Это ~80 ядер и ~250 ГБ RAM,
которые в классической «клиент-сервер» схеме не делают ничего.

ТЗ это прямо благословляет: «возможность горизонтального масштабирования
(добавление узлов в локальный кластер)» и «отказоустойчивость компонентов при выходе
из строя отдельных узлов». Мы не изобретаем обходной путь — мы буквально выполняем требование.

### 2.1 Что выносится на узлы, а что нет

Разделение идёт **по границе доверия, а не по удобству**.

| Нагрузка | Где | Почему |
|---|---|---|
| Генерация сценариев (LLM) | **узел, только в простое** | главный и единственный настоящий bottleneck |
| Предрендер TTS (piper) | **узел, только в простое** | линейно параллелится, ×20 |
| ASR реплик оператора (whisper.cpp) | **узел, во время занятия** | 1 поток на свой АРМ — посильно |
| Живые подсказки при наборе (орфография, согласование) | **узел, локально** | мгновенно, снимает keystroke-трафик с сервера |
| **Итоговая оценка** | **только сервер** | машина обучающегося не принимает решений о его оценке |
| БД, эталоны, аудит, состояние сессии | **только сервер** | источник истины |

**Что распределять не нужно.** Оценка карточки стоит ~5 мс, а темп — одна карточка
на обучающегося за 30 с. При 20 сессиях это 0.67 вызова/с × 5 мс ≈ **0.3% одного ядра**.
Оценка никогда не была узким местом, и выносить её на края — значит менять
бесплатную вещь на дыру в доверии. Не делаем.

### 2.2 Что это даёт в цифрах

Комплект на занятие: 30 сценариев с эталонами + TTS всех реплик.

| Режим | Генерация | TTS | Итого |
|---|---|---|---|
| Централизованно, i5, LLM 1.5B | ~15 мин | ~7.5 мин | **~22 мин** |
| 20 узлов, LLM 1.5B | ~45 с | ~25 с | **~70 с** |
| 20 узлов, LLM 7–8B Q4 | ~3.5 мин | ~25 с | **~4 мин** |

Последняя строка — самое важное следствие. Модель 7–8B, отвергнутая при расчёте
на одну машину (минуты на сценарий), в кластере становится рабочей,
а качество русского текста у неё несопоставимо выше, чем у 1.5B.

### 2.3 ASR перестаёт быть опцией

**Как сделано в итоге (узел 9):** распознавание — на сервере, Vosk с малой русской моделью и словарём разговора
оператора, а не whisper на узлах: 20 одновременно говорящих занимают 0,6 ядра 4-ядерного сервера, итог — через
0,5 с после конца речи (пауза конца фразы); вопрос определяется по основам слов. Замеры и допущения — `ASSUMPTIONS.md` §9,
`LOADTEST.md`. Ниже — исходный замысел.

Ранее распознавание речи было помечено как неподъёмное — но этот вывод исходил
из предположения, что whisper.cpp крутится на сервере (20 потоков на одном i5 действительно
невозможны). На своём АРМ это **один поток на одного обучающегося**, и картина другая.

Ключ к бюджету: нам **не нужен точный транскрипт**, нам нужен чек-лист слотов —
представился ли оператор, уточнил ли адрес, спросил ли о пострадавших, о наличии угрозы.
Для этого достаточно `whisper base` (~150 МБ, RTF ~0.3 на двух потоках) плюс наши газетиры
и fuzzy-сопоставление: ошибка ASR в окончании слова нам безразлична.
Распознавание идёт **не потоково, а по репликам** (VAD отсекает реплику оператора),
результат нужен к моменту закрытия карточки, а не мгновенно.

Это качественный скачок продукта: оценивается не только то, **что оператор написал
в карточке**, но и то, **что он спросил у заявителя** — то есть собственно навык,
которому учат операторов 112.

### 2.4 Граница доверия

Обучающийся имеет физический доступ к своей машине, значит всё, что там считается, —
потенциально подделываемо. Разделение:

- **Решения об оценке принимает только сервер.** Узел не считает баллы.
- **Подсказки при наборе — advisory.** Их подмена не влияет ни на что, кроме удобства.
- **Транскрипт ASR — это данные, а не оценка.** Аудио и так уходит на сервер для записи
  занятия, поэтому сервер может перепроверить выборочно. В режиме аттестации
  (`strict_mode`) ASR принудительно считается на сервере: аттестуемых единицы, не 20.
- **Артефакты генерации** валидируются схемой карточки и утверждаются преподавателем —
  подделать их незаметно нельзя.
- Каждый узел подписывает результат ключом, выданным при регистрации; всё попадает в аудит.

### 2.5 Механика

- `a112-node` — агент на АРМ: тот же `libarm112` плюс тонкий Python-обвяз. **Одна кодовая база,
  разные роли** — сервер и узел отличаются конфигурацией, а не кодом.
- Агент регистрируется на сервере и публикует профиль: ядра, свободная RAM, набор SIMD,
  текущее состояние (`в занятии` / `свободен`).
- Сервер держит очередь задач: `generate_scenario`, `render_tts`, `batch_rescore`, `compile_dict`.
  Задачи уходят **только на узлы в состоянии «свободен»**.
- **Во время занятия АРМ не берёт фоновых задач.** Приоритет — отклик интерфейса своего
  обучающегося (норматив ТЗ — 2 с). Распределение работает в окнах: подготовка, перемены, ночь.
- Задача = `(seed, шаблон, параметры, версия модели)`. Результат — контент-адресуемый артефакт
  по BLAKE3-хешу, что даёт дедупликацию и повторяемость бесплатно.
- Таймаут и переназначение задачи закрывают требование ТЗ об отказоустойчивости узлов буквально.
- Модели и словари ставятся один раз офлайн-инсталлятором (он всё равно нужен для каждого АРМ),
  поэтому раздавать гигабайты по сети не требуется. P2P-раздача чанков остаётся опцией
  для обновлений, а не обязательным механизмом.

### 2.6 Обязательная деградация в одну машину

Класс может оказаться из трёх машин, или АРМ могут быть тонкими клиентами.
Поэтому **режим «узлов нет» — не аварийный, а штатный**: всё считается на сервере,
просто медленнее. Один и тот же код, разница только в том, кто взял задачу из очереди.
Ветвления «если кластер / если один» в бизнес-логике быть не должно.

## 4. Бюджет оперативной памяти

### 4.1 Сервер, худший случай: 8 ГБ, всё на одной машине, узлов нет

| Компонент | RSS |
|---|---|
| ОС (Windows 10/11 или Ubuntu) в простое | 1.5–2.5 ГБ |
| PostgreSQL (`shared_buffers=256MB`, `work_mem=8MB`, `max_connections=50`) | ~400 МБ |
| Python API, 2 воркера | ~350 МБ |
| libarm112: приватный RSS + разделяемые mmap словарей | ~120 МБ |
| rtpd + предрендеренное аудио (page cache, вытесняемо) | ~80 МБ |
| Браузер с открытым АРМ-112 | 400–700 МБ |
| **Пик во время занятия** | **~3.0–4.2 ГБ** |
| genworker с LLM — **только вне занятия** | +1.3 ГБ |

Приёмы, которые делают этот бюджет реальным:

- Словари, эмбеддинги и газетиры — **`mmap` read-only**, разделяются между воркерами, страницы вытесняемы под давлением.
- genworker **спавнится по запросу и завершается**; резидентного LLM-сервиса нет.
- Аудио реплик **предрендерится в WAV на этапе генерации сценария** и кэшируется по хешу `(текст, голос)`. Во время занятия синтеза нет вообще.
- Никакого Docker Desktop / WSL2 на Windows-стенде: он один съедает ~2 ГБ из 8.

Это самый тяжёлый из возможных режимов. В кластере генерация уходит на узлы,
и серверу остаётся ~2.5 ГБ — то есть требование ТЗ «сервер от 32 ГБ» перестаёт быть
обязательным, сервером может быть такой же i5.

### 4.2 АРМ обучающегося (8–16 ГБ)

| Компонент | RSS |
|---|---|
| ОС в простое | 1.5–2.5 ГБ |
| Браузер с АРМ-112 | 400–700 МБ |
| `a112-node`: libarm112 + mmap словарей | ~120 МБ |
| whisper.cpp `base` int8, 2 потока | ~180 МБ |
| **Пик во время занятия** | **~2.2–3.5 ГБ** |
| [в простое, занятия нет] llama.cpp 7–8B Q4 | +4.5 ГБ |
| [в простое] llama.cpp 1.5B Q4 | +1.1 ГБ |

Два режима АРМ **никогда не пересекаются**: узел берёт задачу генерации только
в состоянии «свободен». Поэтому 7–8B помещается даже в 8 ГБ, а на 16 ГБ — с запасом.

## 5. Бюджет латентности оценки карточки

Цель — ≤200 мс при нормативе ТЗ 2000 мс (запас ×10).

| Этап | Время |
|---|---|
| Токенизация + лемматизация ~300 токенов (FSA, ~1.5 мкс/токен) | 0.5 мс |
| Снятие омонимии (перцептрон, ~50 КБ модель) | 0.3 мс |
| Орфография: Levenshtein-автомат только по OOV (~5 слов) | 2.0 мс |
| Проверка согласования по морфотегам | 0.2 мс |
| Сопоставление ~30 полей с эталоном (Myers + token-set + cosine) | 1.5 мс |
| Скоринг (рубрика / GBDT) | 0.02 мс |
| **Итого ядро C** | **~5 мс** |
| Python: сериализация, запись события, ответ | ~30 мс |
| **Итого end-to-end** | **~35 мс** |

При 20 параллельных сессиях и отпущенном GIL четыре ядра загружены на единицы процентов.

## 6. Что именно пишем на C и почему

Не «C ради C», а только там, где это даёт порядок величины.

### 6.1 `morph` — русская морфология
FSA/DAWG, собранный из словаря OpenCorpora, `mmap` read-only, ~25 МБ.
Функционально это то же, что даёт pymorphy, но без создания Python-объектов — выигрыш ×100–1000.
Без этого проверка грамматики за 5 мс невозможна в принципе.

### 6.2 `tagger` — снятие морфологической омонимии
Усреднённый перцептрон по тегам OpenCorpora, модель ~50 КБ.
Нужен, потому что словарь даёт все разборы, а для проверки согласования нужен ровно один.

### 6.3 `spell` — Levenshtein-автомат
Автомат расстояния k=1..2, пересекаемый с DAWG обходом в глубину.
Запускается **только по словам вне словаря**, поэтому средняя стоимость низкая.
Выдаёт кандидаты замены с ранжированием по частоте и клавиатурной близости.

### 6.4 `match` — сравнение с эталоном
- **Myers bit-parallel** — редакционное расстояние за `O(n · ceil(m/64))`. Один из немногих случаев, где битовый параллелизм честно даёт ×20 и где ручной asm вообще имеет смысл (`_addcarry_u64` для строк длиннее 64 символов).
- token-set ratio и Jaro-Winkler для коротких полей (ФИО, названия служб).

### 6.5 `embed` — семантическое сходство без нейросети
Статическая таблица эмбеддингов: 64 измерения, int8, ~25 МБ на ~200 тыс. лемм.
Косинус на AVX2 (`_mm256_maddubs_epi16` + горизонтальная свёртка).
Покрывает свободный текст («описание», «принятые меры»), где точное совпадение бессмысленно.

### 6.6 `slots` — извлечение фактов
Aho-Corasick по газетирам: улицы и объекты Москвы, типы происшествий, экстренные службы, синонимы.
Один проход по тексту, независимо от размера словаря паттернов.

### 6.7 `evlog` — событийный лог
mmap-кольцо, записи фиксированной длины 64 байта, lock-free SPSC на сессию.
Закрывает **сразу четыре требования ТЗ** одним механизмом:

1. аудит действий пользователей (хранение 6 месяцев);
2. буферизация при сбоях БД;
3. восстановление сессии после обрыва сети до 30 с без потери данных;
4. **полное воспроизведение записи занятия** для преподавателя — ключевая демонстрационная возможность.

Хеш-цепочка **BLAKE3** (не SHA-256: на Coffee Lake / Comet Lake нет SHA-NI, BLAKE3 на AVX2 быстрее в разы) делает журнал tamper-evident.

Пропускная способность: ~1 млн событий/с в лог, ~50 тыс./с через `COPY` в Postgres. Требование ТЗ — 100 операций/с.

### 6.8 `ekp` — движок единого классификатора
Классификатор v.046.24 компилируется в плоскую таблицу: индекс по
`(п1, п2, п3, маска дополнительных признаков)` → итоговый тип + список оповещения.
1283 происшествия × 91 колонка маршрутизации компилируются в таблицу 135 КБ (формат —
`core/src/ekp/FORMAT.md`), поиск — двоичный по коду. Реализовано и сверено с эталоном
на 524 882 входах (`tests/test_ekp_native.py`).
Даёт две вещи сразу: реалистичное поведение АРМ-112 для обучающегося
и эталон маршрутизации для оценки.

Поведенческая деталь со стенда: **список оповещения не появляется, пока набор признаков
не разрешается в конкретный код классификатора** (`UI-SPEC.md` §23). Пока каскад неполон —
маршрутизации нет. Это надо воспроизвести: обучающийся должен видеть, что список служб
возникает как следствие его выбора, а не появляется сразу.

### 6.9 `fsm` — автоматы статусов: оставлен на Python
Автомат статусов реагирования и автомат статусов карточки (§10.2).
Проверяет допустимость перехода, обязательность комментария, оба таймера.
Таблица переходов — данные, а не код (`data/fsm/response_status.json`).

**Решение по ходу реализации: в C не переносим.** Автомат вызывается один раз на действие
человека — раз в несколько секунд на участника, это не горячий путь, и выигрыша от C нет.
Работает эталон `pycore/arm112/reference/fsm.py`, им пользуются и движок занятия, и оценка.
Вернёмся к переносу, только если понадобится пакетная проверка журналов (`evlog`)
на тысячах занятий.

### 6.10 `rtpd` — голосовой мост
Минимальный SIP UA (REGISTER, INVITE/180/200/ACK, BYE, CANCEL, OPTIONS), SDP offer/answer, RTP по RFC 3550, адаптивный jitter-буфер 20–80 мс, транскодирование G.711 A/μ-law ↔ PCM16 ↔ Opus.

### 6.11 Про ассемблер — честная позиция
Порядок работы: **портируемый C → AVX2-интринсики с runtime-диспетчеризацией по CPUID → ручной asm только если профайлер докажет, что компилятор не справился.**
Закладываем точки входа для asm-вариантов (`core/src/simd/`), но не пишем их заранее.
GCC/Clang с `-O2 -march=haswell` векторизуют большинство наших циклов не хуже человека; реальные кандидаты на ручную работу — внутренний цикл Myers и свёртка int8-косинуса, и там достаточно интринсиков.

## 7. Голосовой канал: почему WS-audio, а не WebRTC

Изначальная формулировка — «WebRTC + мост». Ниже — уточнение, сохраняющее функциональность и убирающее целый слой риска.

**WebRTC в изолированном контуре не даёт своих преимуществ.**
STUN/TURN не нужны (NAT между АРМ и сервером нет), DTLS-SRTP дублирует уже имеющийся TLS, а ICE добавляет время установления соединения и целый класс отказов. Плюс собственную реализацию WebRTC-стека за 1–2 недели не написать, а тянуть внешний — это +несколько МБ зависимостей и чужие баги.

**Решение: WebSocket-аудио.**
Браузер: `AudioWorklet` → PCM16 @ 16 кГц → бинарные фреймы по 20 мс → WSS.
256 кбит/с на сессию; при 20 сессиях — 5 Мбит/с в гигабитной сети, то есть ~0.5% канала. Кодек на клиенте не нужен вообще.

**Бюджет задержки:** фрейм 20 мс + LAN <1 мс + jitter-буфер 40 мс ≈ **60 мс** при нормативе ТЗ 150 мс.

**Что остаётся на C:** `rtpd` обслуживает SIP/RTP-сторону для реальных IP-телефонов и мостит её с WS-стороной, транскодируя G.711 ↔ PCM16. Требование ТЗ о VoIP/SIP закрыто полностью, риск сосредоточен в одном хорошо очерченном демоне, который можно доставить последним, не блокируя демо.

Эхоподавление: по ТЗ используется гарнитура, акустической обратной связи нет, AEC не требуется.

## 8. Модель оценки — рубрика заказчика, а не наша выдумка

Памятка ГБУ «Система 112» содержит готовую систему оценки: четыре правила
проставления статусов и семь категорий нарушений с разобранными примерами.
Изобретать веса не нужно — нужно реализовать то, чем реально меряет
отдел контроля реагирования.

### 8.1 Четыре правила (прямая цитата структуры памятки)

| Правило | Что проверяем машинно |
|---|---|
| **Соответствие фактическому статусу заявки** | статус против факта сценария: если работы не будут проводиться, «Принята» — ошибка |
| **Соответствие компетенции службы** | тип происшествия против зоны ответственности службы обучающегося (берётся из матрицы маршрутизации) |
| **Своевременность** | первичный статус ≤ 30 с; статусы хода работ — по факту событий сценария |
| **Полнота информации** | обязательность и содержательность комментария |

### 8.2 Семь категорий нарушений = классы ошибок в отчёте

1. Отсутствует статус реагирования.
2. Статус не соответствует статусу заявки *(«Принята: не обслуживаем территорию» вместо «Не принята»)*.
3. Отказ от реагирования на профильное происшествие.
4. Нет комментария к «Не принята» / «Отказ от выполнения работ».
5. Комментарий неполный *(не указано, куда передана информация)*.
6. Отсутствуют статусы хода работ и комментарии к ним.
7. Не обеспечена оперативная связь с местом установки АРМ-112.

Каждая категория — отдельный детектор в ядре и отдельная строка в отчёте
преподавателя. Примеры из памятки идут в комплект поставки как готовые учебные
сценарии: у них уже есть и завязка, и правильный ответ, и разбор ошибки.

### 8.3 Три слоя проверки

**Слой 1. Классификация и маршрутизация.** Главная ось, а не текст.
- совпадение кода `Г/п1/п2/п3` даёт четыре уровня частичного зачёта
  (угадал группу / первый признак / второй / точно) — метрика вытекает из самого кода;
- список оповещения сравнивается **как множество**: пропущенная служба — false negative
  (опасно), лишняя — false positive (памятка прямо называет избыточное оповещение
  проблемой). Отсюда precision / recall по службам — те же метрики, которыми
  пользуется отдел контроля.

**Слой 2. Слоты карточки.** Метрика по типу поля:

| Тип поля | Метрика |
|---|---|
| признак каскада | точное совпадение по коду уровня |
| адрес | нормализация по газетиру и ориентирам + fuzzy |
| число, телефон, время | нормализация + точное сравнение |
| ФИО, название службы | Jaro-Winkler + token-set |
| описание, комментарий | покрытие обязательных фактов + косинус эмбеддингов |

**Слой 3. Форма и регламент.** Орфография, согласование, обязательность комментария
для отказных статусов, корректность переходов автомата, оба таймера.

### 8.4 Что оценивается в режиме ДДС

Заказчик уточнил: карточку ДДС не проверяет и не редактирует (§10.7). Поэтому в режиме ДДС
оценка строится вокруг статусов и связи с бригадой:

| Что | Как проверяем |
|---|---|
| Первичный статус | ≤ 30 с с момента поступления карточки |
| Решение «Принята» / «Не принята» | против профильности: входит ли служба обучающегося в маршрутизацию карточки не только как информационный получатель |
| Отказ | комментарий обязателен и содержит, куда передана информация (нарушения №4 и №5 памятки) |
| Соответствие статуса докладу бригады | доклад «прибыли» → «Прибытие», а не «Проведение работ»; задержка от доклада до статуса |
| Проактивность | если бригада молчит дольше заданного интервала — позвонил ли диспетчер сам |
| Комментарии | орфография и согласование — это единственный свободный текст ДДС |

### 8.5 Итоговый балл

**По умолчанию — прозрачная рубрика** с весами по семи категориям нарушений,
настраиваемая преподавателем (ТЗ: «пороги допустимых ошибок, требования
к синтаксису ответов»). GBDT включается опционально, когда накоплены размеченные
преподавателем примеры; на старте их нет, и делать вид, что есть, было бы нечестно.

Ключевое свойство сохраняется: **каждый снятый балл называется словами заказчика**
и ссылается на конкретное правило памятки.

## 9. Генерация сценариев и обработка правок преподавателя

### Комбинаторный движок (основа)
`1139 доступных оператору типов из классификатора × локация (газетир Москвы) × время суток ×
дополнительные признаки (УЛ / ПП / НД и т.д.) × персона заявителя × осложняющий фактор`
даёт тысячи структурно валидных сценариев без единого вызова LLM.
Структура берётся не из головы, а из классификатора v.046.24, поэтому эталонный
итоговый тип и список оповещения вычисляются модулем `ekp`, а не выдумываются.

### LLM (поверх)
llama.cpp с **GBNF-грамматикой**, выводящей строго валидный JSON по схеме карточки.
Задача LLM — только текст реплик заявителя и описаний, не структура. Это снимает главный
риск малых моделей — сбой формата.

**96 билетов работают как few-shot-эталон стиля**: модель не сочиняет жанр с нуля,
а продолжает известный. Сгенерированный вызов затем проверяется на статистическую
неотличимость от билетов (длина, состав слотов, наличие ориентира, ФИО, телефона);
не прошедший проверку отбраковывается до показа преподавателю.

### Цикл валидации преподавателем (сценарий из ТЗ)
1. Преподаватель выбирает категории событий и запускает генерацию.
2. Система формирует сценарии и **эталонные ответы**.
3. Предпросмотр с подсветкой правильных вариантов.
4. **Коррекция**: преподаватель вводит свободный комментарий → `комментарий + текущая карточка + схема` → genworker → новая версия → **diff показывается преподавателю** → подтверждение.
5. Версии сценариев неизменяемы, каждая несёт `approved_by` и `approved_at`.

### Предрендер аудио
Утверждённые реплики сразу синтезируются piper TTS в WAV и кэшируются по хешу `(текст, голос)`.
Во время занятия синтеза не происходит.

Первый замер (piper 1.8, голоса `ru_RU-dmitri/ruslan/irina-medium`, onnxruntime на CPU):
11–15 с речи синтезируются за 0,7–0,8 с на серверном Xeon — в 17–19 раз быстрее реального
времени; на i5 ожидаем в несколько раз медленнее, что для предрендера с запасом. Голос — 63 МБ.

Реализация (узел 5, `server/speech/`): процесс `python -m speech.render` в объекте задания Windows
(одно ядро, приоритет ниже обычного, память до 1 ГБ), кэш `var/tts/<хеш>.wav`, телефонная линия
8 кГц. Замеры на ядре Xeon Gold 6240R (та же микроархитектура Skylake, что у i5 8–10 поколения,
но есть AVX-512 и ниже частота — цифры ориентировочные, точные даёт `tools/demo_call.py` на демо-ноутбуке):
- встроенный набор — 759 фраз, 70 минут речи, 67 МБ WAV; фоном на одном ядре — в 5–6 раз быстрее
  реального времени, около 13–15 минут один раз (на следующих запусках — из кэша);
- память: голос без арены onnxruntime ≈ 200 МБ, пик процесса 414 МБ; с ареной память росла до 1,2 ГБ
  за 60 фраз, реплика в 290 символов одним куском требовала 1,2 ГБ — поэтому арена выключена,
  длинные реплики синтезируются частями до 110 символов;
- OpenBLAS резервирует буфер на каждое ядро машины (на 16 ядрах ~480 МБ) — потоков BLAS столько же,
  сколько потоков синтеза.
Что учесть в поставке:
- **VC++ runtime.** onnxruntime ≥ 1.18 требует `msvcp140_1.dll`, которой нет на Windows без
  свежего Visual C++ Redistributable; кладём библиотеки рядом с onnxruntime или ставим
  Redistributable инсталлятором.
- **Лицензии.** Актуальный piper (`piper-tts` ≥ 1.3) — GPL-3.0, фонемизатор espeak-ng — тоже GPL;
  у голосов свои лицензии датасетов. Для поставки заказчику решаем до сборки инсталлятора.

## 10. Предметная модель: она восстановлена из первичных документов

Главный риск проекта — «мы не знаем, как устроен настоящий АРМ-112» — **снят**.
Заказчик дал три первичных источника, перечисленных в ТЗ §11:

| Документ | Что из него получено |
|---|---|
| `Классификатор происшествий v.046.24` | 1283 типа происшествий в 24 группах, каскад признаков, матрица маршрутизации в 58 служб |
| `Классификатор происшествий v.046.11` | предыдущая версия (52 службы) — **regression-фикстура** для подмены классификатора |
| `Работа с АРМ-112. Памятка для ДДС` | автоматы статусов, правила, **таксономия нарушений** |
| `Билеты-задачи по С-112` | 96 реальных учебных вызовов с формулировками заявителей |
| **`Инструкция по заведению карточки`** | **официальный функционал модуля: 42 раздела, горячие клавиши, правила, телефония** |
| **29 снимков стенда УМЦ, 17.09.2026** | **живой интерфейс 1920×1080, все состояния** |
| `РТУ Т16Р Datasheet` | аппарат на рабочем месте: 20 SIP-линий, Opus / G.711, DTMF RFC2833 |

### 10.1 Классификатор — не дерево, а матрица решений

Код происшествия — семь цифр `Г пп1 пп2 пп3`, где каждая пара — уровень каскада,
который оператор проходит в интерфейсе:

```
2010901  ->  Г=2  ДТП
             п1=01  «ДТП»                    (112-Признак.1)
             п2=09  «Наезд на препятствие»   (112-Признак.2)
             п3=01  «Столб, мачта освещения» (112-Признак.3)
        ->  итоговый тип: «ДТП наезд на опору освещения», главная служба Police
```

24 группы, 1283 строки, из них **1139 доступны оператору** (остальные — служебные,
помечены «Не отображается оператору 112»). Код — семь или восемь цифр: у групп 10–24
номер группы двузначный. У группы 24 «БПЛА» нет строки-заголовка, её имя берётся из строк.
Дальше идёт 91 колонка маршрутизации:
служба × условие. Условия — это те самые дополнительные признаки
(`НД — нет доступа`, `УЛ — угроза людям`, `ПП — пострадавшие/погибшие`,
`перекрытие движения`, `тоннель`, `газификация` и т.д.).

Без дополнительных признаков на АРМ-112 видно **в среднем 4,5 службы** на происшествие,
максимум 15. Заполненных колонок маршрутизации у происшествия в среднем 17,5, но большая часть
из них — условные (срабатывают от признаков) или информационные получатели, которых на АРМ не видно.
Список оповещения формируется автоматически по ЕКП — ровно это и написано в памятке.

Версии классификатора различаются мало: в `v.046.11` 1281 код, в `v.046.24` — 1283
(добавлены «Прочие происшествия (от 102)» и «БВС Регион»). Служб в шапке 51 и 58:
добавлены ЦУКБ Минобороны, **ЦУКБ.БПЛА Минобороны**, ГКУ «Организатор перевозок»,
Мосэкомониторинг, Минобороны РХБЗ, Ситиэнерго, Депгражданстроительства, «РЖД» переименована
в «РЖД (МосковскаяЖД)». Колонки в версиях сдвинуты: в `v.046.11` есть «Сценарий реагирования»
(741 код на 1260 происшествиях), в `v.046.24` её нет, — поэтому сборщик находит колонки по заголовкам.
Рабочей берём `v.046.24`, а `v.046.11` оставляем как **regression-фикстуру**:
подмена классификатора без пересборки — заявленное свойство, и его надо проверять тестом.

Нормализованный вид: [`data/classifier/classifier.json`](../data/classifier/classifier.json).
В C компилируется в плоскую таблицу с индексом по `(п1, п2, п3, маска флагов)` —
поиск — двоичный, таблица 135 КБ в памяти (§6.8).

**Следствие:** мы воспроизводим поведение настоящей системы точно, а не правдоподобно.
Обучающийся выбирает признаки — и видит тот же список оповещения, который построил бы
реальный АРМ-112.

### 10.2 Автомат статусов реагирования

Памятка задаёт его однозначно, включая запрет на пропуск шагов:

```
            ┌─ Не принята ──► Принята            (единственный переход)
Добавлена ──┤   (коммент. обязателен)
(авто)      └─ Принята ──► Начало реагирования ──► Прибытие ──►
                           Проведение работ ──► Работы завершены  [карточка закрыта]
                                              └─► Отказ от выполнения работ [закрыта,
                                                  комментарий обязателен]
```

Статусы карточки — второй автомат: `Зарегистрирована → Отработана → Проверена`,
плюс проблемные `Не оповещено` (никто не ответил вовремя), `Отказ`,
`Не завершено` (прошло 48 часов), `Завершена`.

Правило доступности переходов видно на стенде напрямую (`UI-SPEC.md` §25):
в выпадающем списке предлагаются **следующий по порядку статус и два терминальных**
(«Отказ от выполнения работ», «Работы завершены»). То есть «последовательно» из памятки
означает «только вперёд»: перепрыгнуть к завершению можно, вернуться назад — нет.

Оба автомата описываются данными, проверяются модулем `fsm` (§6.9) и **являются предметом оценки**:
некорректный переход — это ошибка, а не просто заблокированная кнопка.
Живой эталонный трек статусов с таймингами (`UI-SPEC.md` §26) забираем как тест-фикстуру.

### 10.3 Норматив 30 секунд означает не то, что казалось

ТЗ говорит «временные рамки выполнения заданий, по умолчанию — 30 сек».
Памятка уточняет: 30 секунд — это срок **проставления первичного статуса реагирования**
(`Принята` / `Не принята`) после поступления карточки в службу. Не время заполнения карточки.

Отсутствие статуса в этот срок переводит карточку в состояние «Не оповещено»
и подсвечивает её красным в разделе отдела контроля.

Поэтому таймеров в системе два, и мерить надо оба:
- **30 с** — до первичного статуса (жёсткий регламентный, из памятки);
- **время заполнения карточки** — стартует при открытии новой карточки, останавливается
  по кнопке «Сохранить», сохраняется и попадает в отчёты. При превышении норматива
  **блок таймера в интерфейсе краснеет**. По кадрам стенда порог лежит между
  **63 и 83 секундами** (`01:03` ещё чёрный, `01:23` уже красный), то есть это не ровно
  минута и, возможно, значение зависит от типа происшествия — см. `UI-SPEC.md` §24.
  У нас норматив делается **параметром схемы карточки**, настраиваемым преподавателем.
  Это и есть «отличие времени от нормативного» из ТЗ.

### 10.4 Билеты как корпус и как эталон стиля

**Транскрибированы полностью**: 32 билета × 3 вызова = **96 вызовов**,
[`data/scenarios/bilety.json`](../data/scenarios/bilety.json).
Формат билета — «Отработайте вызовы от заявителя», таблица `№ | Ситуация | Адрес`.

Статистика корпуса:

| Показатель | Значение |
|---|---|
| Вызовов | 96 |
| С телефоном заявителя | 96 (100%) |
| С нормализованным адресом в скобках | 20 |
| Москва | 63 |
| Московская область | 11 |
| Другой регион (не зона ответственности) | 8 |
| Адрес требует уточнения (описательный, без города) | 14 |
| Указана роль заявителя (очевидец, прохожий, сосед…) | 22 |

Что из этого следует:

- Это **seed-корпус** — занятие можно провести вообще без генерации.
- Это **эталон стиля для LLM**: few-shot расширение известного стиля вместо
  сочинения с нуля. Малая модель на такой задаче работает несопоставимо лучше.
- Это **валидационный набор для генератора**: сгенерированный вызов должен быть
  статистически неотличим от билетов по длине, составу слотов, наличию ориентиров.
- Там есть **непрофильные вызовы** («поругался с продавцом „Мегафон“, бросил трубку»)
  и **вызов не по территории Москвы** (Волгоградская обл.). То есть отсев
  и определение зоны ответственности — отдельный оцениваемый навык.
- **Есть намеренные повторы одной ситуации с разными адресами.** Вызов
  «ДТП, Б/П, Б/Р, пежо + фольксваген» встречается в билетах 25–28 четыре раза:
  МКАД ×2 и Садовое кольцо ×2, причём один из них — «въезд в тоннель»,
  а `тоннель` в классификаторе является условием маршрутизации. То есть методика
  заказчика прямо тренирует зависимость «адрес → дополнительный признак → другой
  список оповещения». Это подтверждает, что главная ось оценки — классификация
  и маршрутизация, а не текст.
- **8 вызовов не из зоны ответственности** (Волгоградская, Рязанская, Тульская,
  Владимирская обл.) и **14 с адресом, который нельзя принять как есть** —
  это отдельный оцениваемый навык, а не шум в данных.
- Адреса даны **как их называет заявитель**, с нормализованным вариантом в скобках:
  «рядом с посольством Азербайджана на тротуаре *(Леонтьевский переулок, дом 16, стр. 1)*»,
  «МКАД между 74 и 68 км», «набережная Яузы, в область, напротив Большого Нижнего пруда».
  Это готовые обучающие пары «сказано → записано» для модуля нормализации адреса —
  именно та задача, под которую задумывался газетир.

### 10.5 Интерфейс снят со скриншотов памятки

Памятка содержит 31 скриншот боевого АРМ-112, включая аннотированный разбор строки ленты
карточек со всеми колонками. Подробная спецификация — [`docs/UI-SPEC.md`](UI-SPEC.md),
снимки экранов хранятся локально в `docs/ui/` и в репозиторий не входят.

Главное открытие: **опросная карта и матрица маршрутизации — две проекции одной модели**.
Вопросы опросной карты делятся ровно на две группы:

- «что и где» (`Где`, `Признак пожара`, `Дом (пламя, дым)`, `Внутридомовые объекты`) —
  это уровни кода `Г / п1 / п2 / п3`, они дают **итоговый тип происшествия**;
- да/нет (`Угроза людям`, `Есть ли перекрытие движения`, `Проведена ли газификация`,
  `Доступ`) — это **условия маршрутизации**, то есть буквально колонки матрицы,
  которые в классификаторе так и называются.

Значит опросная карта **генерируется из `classifier.json`** — и не только состав кнопок,
но и тип вопроса (один из / несколько / да-нет / число / текст). Уточнение по снимкам 2026:
по части вопросов **выбор множественный** (на живом примере одновременно отмечены
«Квартира», «Газовая колонка», «Подъезд»), так что это теги, а не строгий каскад.
Нужен слой соответствия `ui_label ↔ код уровня`: формулировки в интерфейсе
и в классификаторе различаются (в UI «Дом многоквартирный», в классификаторе «жилой дом»).

Второе: **вид ДДС и вид оператора 112 — разные экраны**. У ДДС почти всё read-only,
работа сводится к карандашу в блоке своей службы и проставлению статуса.
Третье: **карточки от внешних систем (ВИС) выглядят иначе** — нет формализованных
признаков, только текст, нет № АРМ. Это надо воспроизвести: такая карточка объективно
сложнее для диспетчера, и это учебный материал.

### 10.6 Схема карточки остаётся данными

Принцип не меняется, меняется источник: схема теперь не реконструируется, а выводится
из документов заказчика.

- `data/classifier/classifier.json` — классификатор и матрица маршрутизации;
- `data/schema/card.schema.json` — поля карточки, типы, обязательность, метрика сравнения;
- `data/fsm/*.json` — оба автомата статусов;
- `data/scenarios/bilety.json` — корпус билетов;
- `data/gazetteer/*` — улицы, объекты, ориентиры, службы, синонимы.

UI карточки, валидация, метрики и отчёты генерируются из этих файлов.
Обновление классификатора заказчиком (а он версионируется — `v.046.24`) —
это подмена файла, а не пересборка. Заодно закрывает критерий
«возможность интеграции в любые другие системы».

### 10.7 Роль диспетчера ДДС — ответ заказчика

Главный вопрос предметной области — что именно делает диспетчер ДДС — закрыт
письменным ответом заказчика (переписка с заказчиком — внутренний материал, в репозиторий не входит).
Команда предложила определение (ДДС — звено между оператором 112 и выездной бригадой)
и алгоритм; заказчик подтвердил с существенными поправками:

| Вопрос | Ответ заказчика |
|---|---|
| Проверяет ли ДДС правильность заполнения карточки? | **Нет.** Это прерогатива оператора 112 и службы контроля 112 |
| Что делает ДДС в системе? | **Только выбирает статусы** в нижней полосе и добавляет к ним свои комментарии |
| Как выбирается бригада? | У оператора 112 службы подтягиваются автоматически; **у ДДС бригады выбираются вручную** |
| Канал связи с бригадой | В жизни — что угодно, включая служебные сотовые; **для тренажёра — только IP-телефон** |
| Откуда ДДС узнаёт о ходе работ? | **Старший группы сам звонит и докладывает**, либо **диспетчер через время звонит старшему** — «работают, как правило, два варианта» |
| Связь с заявителем | По телефону напрямую, минуя 112 — номер есть в карточке |
| Специфика служб | «Специфики нет. **Пусть будет универсальный алгоритм для всех**» |

Что это меняет в тренажёре:

1. **Грамматику в режиме ДДС проверяем в комментариях к статусам**, а не в карточке —
   карточку ДДС не редактирует. В режиме оператора 112 проверяется сама карточка.
   Живой пример ровно такой ошибки уже есть: «Отправлн сантехник» в комментарии к статусу.
2. **Источник информации для статусов теперь известен — это звонок старшего бригады.**
   Значит тренажёр обязан эмулировать не только заявителя, но и **старшего бригады
   как собеседника**: входящие доклады по таймлайну сценария («выехали», «прибыли»,
   «приступили», «закончили») и ответы, когда диспетчер звонит сам.
   Для этого у нас уже есть весь конвейер: генерация реплик, предрендер TTS,
   голосовой канал, распознавание речи на АРМ.
3. **Проактивность оценивается.** Если бригада молчит, диспетчер должен позвонить сам;
   интервал контроля становится метрикой.
4. **Один универсальный алгоритм ДДС на все службы** — огромное сокращение объёма.
   Различия между службами — только в том, какие карточки им профильны,
   а это уже вычисляет маршрутизация.

Цикл диспетчера ДДС в тренажёре, итого:

```
карточка в ленте ─► ≤30 с: «Принята» / «Не принята» + комментарий
                     │
                     ├─ «Не принята»: обоснование + куда передано  → конец
                     │
                     └─ «Принята» ─► выбрать бригаду, позвонить старшему (IP-телефон)
                                     │
                         ┌───────────┴────────────┐
                 старший звонит сам      диспетчер звонит через N минут
                         └───────────┬────────────┘
                                     ▼
                  статус по факту доклада + комментарий (грамматика, полнота)
                  Начало реагирования → Прибытие → Проведение работ → Работы завершены
                  (или «Отказ от выполнения работ» с обоснованием)
```

### 10.8 Маршрутизация: три слоя, первый проверен на стенде

Заказчик сформулировал правило словами: «службы подтягиваются по принципу района
обслуживания и по признаку подчинённости» — и дал пример: пожар в школе в Щукино
с пострадавшими уходит в 01, 02, 03, в ДДС Департамента образования (школа ему
подчиняется), в ДДС управы Щукино и в ДДС Северо-Западного округа.

Вместе с классификатором и снимками стенда это даёт модель из трёх слоёв:

| Слой | Чем определяется | Откуда данные | Статус |
|---|---|---|---|
| **1. Тип и признаки** | код классификатора + флаги опросной карты (угроза людям, правонарушение, газификация, нет доступа, тоннель…) | `classifier.json` | **проверен на стенде** |
| **2. Район обслуживания** | адрес → район/поселение и округ → ДДС района + ДДС префектуры + ГБУ «Автодороги» округа | справочник служб + газетир | правило подтверждено снимком, реализация — через газетир |
| **3. Подчинённость объекта** | объект по адресу → ведомство (школа → Деп. образования, высотка → ЭВАЖД, объект культуры → Деп. культуры) | реестр объектов | нужен реестр |

**Слой 1 проверен автоматически.** Кадры «КАРТОЧКА 112» — это дифференциальный тест
боевой системы: заказчик переключал по одному признаку и снимал, как меняется список служб.
Эталонная функция маршрутизации [`tools/routing_reference.py`](../tools/routing_reference.py)
на фикстуре [`data/fixtures/stand_routing.json`](../data/fixtures/stand_routing.json) даёт:

> **14 точных совпадений из 16, 2 задокументированных расхождения, 0 ошибок.**

Что именно подтвердилось, и всё — из колонок классификатора, без подгонки:

- «Угроза людям: Да» добавляет **ЦЭМП** (колонка ЦЭМП с условием «угроза людям»);
- «Правонарушение: Есть» добавляет **Службу 102** (колонка МВД «выбран признак Правонарушение»);
- «Газификация: Да» добавляет **Службу 104** (колонка МОСГАЗ «газификация»);
- «Медпомощь» не добавляет Службу 103 — потому что СМП в классификаторе завязана на
  признак «Пострадавшие», а не на медпомощь; стенд ведёт себя так же;
- «Тоннель» для горящего мусора ничего не меняет — Гормост для этого кода не назначен;
- пока каскад не разрешился в код, **служб нет вовсе** (8 кадров);
- информационные получатели (Аппарат Мэра, ФСО, ГКУ НТУ, Мосэкомониторинг, ЦУКБ МО)
  в классификаторе есть, но в полосе не видны — ровно как сказано в памятке:
  «службы, которые собирают информацию для анализа, не отображаются».

**Расхождение одно:** на пожаре общественного транспорта стенд показывает «Деп. ЖКХ»,
а классификатор его не выводит. Эта плашка на всех снимках **серая**, в отличие от
остальных. Рабочая гипотеза — служба добавлена вручную (инструкция различает
автоподбор и ручное добавление цветом). Вопрос вынесен заказчику; в фикстуре
расхождение не спрятано, а описано.

**Слой 2 подтверждён снимком стенда.** На карточке «пожар: квартира» с адресом
в поселении Вороновское второй ряд полосы — «ОАТИ, Поселение Ти…, Поселение Вороновское».
Подпись «Поселение Ти…» усечена; в справочнике ей соответствуют два кандидата —
ДДС префектуры ТиНАО и ДДС Тимирязевского района, и для адреса в ТиНАО подходит только
первый. Получается **ДДС поселения + ДДС префектуры округа** — буквально правило заказчика.
Справочник служб ([`data/services/services.json`](../data/services/services.json), 211 записей)
устроен ровно под это: **125 ДДС районов + 21 ДДС поселений = 146, столько муниципальных
образований в Москве**, плюс 11 ДДС префектур (все округа), 10 ГБУ «Автодороги» по округам,
12 ведомств «по подчинённости» и 4 центральные службы 101–104.

**Слой 3 виден косвенно.** На той же карточке классификатор допускает ЭВАЖД,
Мосжилинспекцию и Мособлгаз, но стенд их не показывает: ЭВАЖД — только для высоток,
Мособлгаз — только для Московской области. То есть значение «карточка-112»
в классификаторе означает **допустимость**, а решает объект и территория.
Для тренажёра это значит: адрес в сценарии обязан нести район, округ и тип объекта —
иначе маршрутизация неполна.

Обе версии классификатора пересобираются одним скриптом
[`tools/build_classifier.py`](../tools/build_classifier.py) — прежнее извлечение
теряло условия служб МВД и СМП (они записаны в другом ряду трёхуровневой шапки);
исправлено, все 91 колонка разобраны без остатка.

### 10.9 «Что случилось?»: половина меню — не происшествия

Полный список верхнего уровня — **51 тип** ([`data/classifier/call_types.json`](../data/classifier/call_types.json)):
28 происшествий и **23 служебных или нецелевых** — «Ошибочно набран номер», «Отмена вызова»,
«Консультация», «Справка 101…104», «Жалоба на действие служб», «Благодарность службам»,
«Тестовый вызов», «Передача дежурства» и т.д.

Отсев нецелевых обращений — существенная часть работы оператора 112, и в корпусе
билетов такие вызовы есть. В режиме оператора 112 это отдельный оцениваемый навык:
правильно распознать, что вызов не требует реагирования, и не отправить его в службы.

## 11. Прогнозирование, рекомендации, диаграммы

Требования финальной экспертизы закрываются на накопленной телеметрии:

- **Прогноз**: по кривой обучения — «оператор выйдет на норматив 30 с примерно через 4 занятия», вероятность успешной аттестации. Модель простая (логистическая регрессия / небольшой GBDT на десятках признаков), обучается за секунды.
- **Проверка достоверности**: система сохраняет прогноз и позднее сопоставляет его с фактом, показывая MAE и калибровку. Это буквально то, что требует ТЗ — «оценка достоверности путём сравнения реальных данных и прогнозных значений».
- **Рекомендации**: кластеризация типов ошибок → адресное назначение тренировок. Групповые инсайты для преподавателя («в группе систематически пропускается уточнение этажа при вызовах в жилой сектор»).
- **Диаграммы**: тепловая карта ошибок «поле карточки × тип происшествия», кривые обучения, распределение времени заполнения относительно норматива, воронка этапов обработки вызова.

### Связывание C и Python
**`ctypes` поверх разделяемой библиотеки `libarm112`**, собственное CPython-расширение не нужно.
`ctypes.CDLL` отпускает GIL на время вызова, так что вызовы из разных потоков идут параллельно.
Накладные расходы `ctypes` — микросекунды на вызов, а оценка вызывается ~1 раз в секунду на весь класс
(§2.1), так что они несущественны.

Выигрыш — в сборке и поставке: ядро собирается **одним CMake** как обычная `.dll`/`.so`,
без setuptools и без привязки к ABI конкретной версии Python. В портативный Windows-бандл кладётся
готовая DLL рядом со встроенным Python, компилятор на стенде не нужен.

Каждой функции ядра соответствует **эталонная реализация на Python** (`pycore/arm112/reference/`).
Тесты сверяют C с эталоном на фикстурах и на полном переборе входов: C обязан совпадать побитово.

```c
typedef struct a112_ctx a112_ctx;

a112_ctx *a112_init(const a112_config *cfg);   /* mmap словарей, один на процесс */
void      a112_free(a112_ctx *ctx);

/* Потокобезопасно: контекст read-only после инициализации.
   Вызывается с отпущенным GIL. */
int a112_evaluate(a112_ctx *ctx,
                  const a112_card   *filled,
                  const a112_gold   *gold,
                  const a112_timing *timing,
                  a112_verdict      *out);
```

`a112_verdict` возвращает по-полевой разбор: балл, покрытые и пропущенные факты,
орфографические ошибки со смещениями и кандидатами замены, нарушения согласования, отклонения по таймингу.

## 14. Безопасность

- TLS внутри контура с локальным CA; скрипт генерации CA и сертификатов в поставке.
- RBAC в БД, JWT с коротким TTL, отдельный refresh-токен.
- Пароли — Argon2id.
- Аудит = событийный лог с хеш-цепочкой BLAKE3, неизменяемый, хранение 6 месяцев.
- Ограничения ролей из ТЗ реализуются как политики, а не как скрытие кнопок в UI:
  администратор не может менять оценки во время активного занятия;
  преподаватель не может менять оценку без записи в журнал аудита.
- Резервное копирование не реже 1 раза в сутки (`pg_dump` + снапшот event-store) по расписанию.

## 17. Размер LLM — политика времени выполнения, а не решение при сборке

Ранее модель была зафиксирована как 1.5–3B исходя из расчёта на одну машину.
Распределение генерации по узлам это ограничение снимает: 7–8B Q4 даёт комплект
занятия за ~4 минуты и заметно лучше пишет по-русски.

Выбирать один размер при сборке не нужно и вредно — состав класса заранее неизвестен.
**В поставку входят обе модели** (~1.1 ГБ + ~4.5 ГБ; при требовании ТЗ «SSD от 256 ГБ» это
несущественно), а размер выбирает диспетчер по профилю узла, который тот и так публикует:

| Условие | Модель |
|---|---|
| Узел свободен, свободной RAM ≥ 6 ГБ | 7–8B Q4_K_M |
| Узел свободен, свободной RAM < 6 ГБ | 1.5B Q4_K_M |
| Узлов нет, считает сервер | 1.5B Q4_K_M |

Побочный эффект: «режим одной машины» автоматически получает быструю модель,
а класс из 16-гигабайтных АРМ — качественную, без единого переключателя в коде
и без отдельной сборки дистрибутива.

## 18. Занятие как локальное лобби

Сессионная модель тренажёра — **локальное лобби с авторитарным сервером**. ТЗ описывает
занятие именно так: участники входят, преподаватель выбирает категории событий,
запускает обучение и завершает его в любой момент, после чего формирует отчёт.

### 18.1 Кто есть кто

| Понятие лобби | У нас |
|---|---|
| Хост | **сервер** — единственный арбитр. Не машина преподавателя; в режиме одной машины (§2.6) могут совпасть |
| Владелец лобби | преподаватель |
| Комната | занятие |
| Слоты и роли | роль участника: оператор 112 или ДДС конкретной службы |
| Боты | заявитель, старший бригады, оператор 112 (если слот не занят человеком) |
| Время | часы сервера |

Два слоя: **постоянный** (LMS: пользователи, группы, задания, результаты, аудит — в БД)
и **сессионный** (занятие: живёт в памяти сервера, каждое событие пишется в `evlog`).
Несколько занятий идут одновременно и изолированы друг от друга: ТЗ прямо запрещает
преподавателю вмешиваться в работу других преподавателей.

### 18.2 Жизненный цикл

```
 черновик ──► набор ──► идёт ──► завершено ──► отчёт
    │          │         │           ▲
    │          │         └───────────┘  преподаватель, в любой момент
    │          └─ участники входят, преподаватель назначает роли
    └─ преподаватель выбирает режим, категории событий, источник карточек, нормативы
```

| Состояние | Что происходит | Кто переводит дальше |
|---|---|---|
| `черновик` | настройка: режим, категории событий (множественный выбор), источник карточек — сгенерированные / сформированные обучающимися / смешанные (ТЗ), нормативы | преподаватель |
| `набор` | участники входят, преподаватель назначает роли | преподаватель — «старт» |
| `идёт` | поток вызовов и карточек, работа участников | преподаватель — «завершить» |
| `завершено` | приём действий закрыт, запись занятия заморожена | система — после расчёта оценок |
| `отчёт` | отчёт о занятии: действия, ошибки, время заполнения, отклонение от норматива, грамматика | — |

Переходы только вперёд. Администратор не может менять ход активного занятия (ТЗ, ограничения роли).

### 18.3 Роли и боты

| Роль | Кто | Что делает |
|---|---|---|
| Оператор 112 | обучающийся **или бот** | принимает звонок заявителя, заполняет карточку, отправляет службам |
| ДДС службы X | обучающийся | лента профильных карточек, статусы, звонки старшему бригады и заявителю |
| Заявитель | бот | звонит оператору 112: реплики из сценария, предрендер TTS (§9) |
| Старший бригады | бот | звонит ДДС с докладами по таймлайну сценария и отвечает на звонок диспетчера (§10.7) |

**Незанятый слот человека закрывает бот.** Оба сценария ТЗ — частные случаи одной модели:

| Сценарий ТЗ | Люди | Боты |
|---|---|---|
| «Проведение занятия (карточки)» | оператор 112 | заявитель |
| «Проведение занятия (действия с карточками)» | ДДС | оператор 112 (карточки из генератора или корпуса), старший бригады |
| **Совмещённое занятие** (расширение) | оператор 112 **и** ДДС | заявитель, старший бригады |

В совмещённом занятии карточка, которую заполнил один обучающийся, уходит по настоящей
маршрутизации к тем, кто играет ДДС нужных служб. Это не требование ТЗ, а следствие модели,
которое достаётся без отдельной разработки.

### 18.4 Правило видимости — это «ролевая модель» из ТЗ

ТЗ: «распределение прав доступа для обучающихся, чтобы в их ленту попадали только
профильные события (например, от Мосводоканала, Москоллектора, управ, служб газа)».

> Карточка попадает в ленту участника с ролью «ДДС X» тогда и только тогда,
> когда X входит в маршрутизацию карточки.

Маршрутизацию вычисляет `ekp` — та же функция, что сверена со стендом (§10.8).
Роли преподаватель выбирает из справочника служб (211 записей, `data/services/services.json`).
Информационные получатели (Аппарат Мэра, ФСО и т.п.) в роли не назначаются —
на боевом АРМ-112 их тоже нет.

### 18.5 Время

**Все отметки времени ставит сервер.** Клиент показывает таймер, но нормативы —
30 с на первичный статус и время набора карточки — считаются по серверным часам и пишутся в `evlog`.
Это защищает оценку от подкрутки часов на АРМ и от рассинхрона машин класса.

### 18.6 Обрыв связи и возврат

- Место участника держится **всё занятие**, а не только 30 с.
- Клиент нумерует свои действия монотонно и буферизует их (сейчас — `sessionStorage` вкладки:
  переживает перезагрузку страницы; IndexedDB понадобится, если надо пережить закрытие браузера).
  При возврате сервер присылает снимок с последним учтённым номером, клиент отправляет
  недостающее; сервер принимает по `(участник, номер)` и отбрасывает повторы. Так выполняется
  требование ТЗ о сбоях до 30 с без потери данных — и боевая система делает так же
  (локальное сохранение карточки при обрыве, инструкция, раздел 8).
- При отсутствии дольше 30 с место помечается «нет связи», таймеры идут: в жизни карточка
  тоже не ждёт. Преподаватель видит это на мониторинге и решает сам. **Бот не подменяет
  человека молча** — иначе оценка обучающегося исказится.

### 18.7 Транспорт и обнаружение

- Браузер ↔ сервер: HTTPS и WebSocket (события занятия), отдельный WebSocket для аудио (§7).
  Токен передаётся **первым сообщением** сокета, а не в адресе: адреса попадают в журналы доступа.
- **Рабочее место — браузер в режиме киоска** (`deploy/kiosk/`): на весь экран, без адресной
  строки и вкладок, со своим профилем. ТЗ требует работу в браузерах (Chrome, Firefox,
  Яндекс Браузер), и боевой АРМ-112 сам работает в браузере, поэтому отдельная программа
  не нужна. Стартовая страница лежит на рабочем месте и ждёт сервер, так что киоск можно
  поставить в автозапуск раньше, чем поднимется сервер.
- **Обнаружение сервера не нужно**: браузер открывает фиксированный адрес — так же,
  как на боевом стенде. Агенты `a112-node` могут находить сервер
  широковещательным UDP-запросом, это удобство, а не требование.
- Задержка в LAN — меньше миллисекунды, поэтому модель событийная, без игрового цикла
  с фиксированным тактом и без предсказания на клиенте.

### 18.8 Два контура на одних машинах

| | Сессионный контур (лобби) | Вычислительный контур (кластер, §2) |
|---|---|---|
| Назначение | занятие в реальном времени | генерация, TTS, пересчёты |
| Когда работает | во время занятия | только когда АРМ свободен |
| Арбитр | сервер | сервер (очередь задач) |

Во время занятия АРМ фоновых задач не берёт, так что контуры друг другу не мешают.

### 18.9 Чем это лобби не является

- **Не P2P и не «клиент-хост».** Иначе арбитром стала бы машина обучающегося,
  а это нарушает границу доверия (§2.4): оценку ставит только сервер.
- **Не игровой сервер с тактом.** Нет физики и предсказания — есть события, таймеры и аудит.

### 18.10 Мониторинг преподавателя

Экран занятия в реальном времени: участники и их роли, состояние связи, очередь карточек
по участникам, нарушения нормативов по мере возникновения, кнопка «завершить».
Закрывает требования ТЗ «контролировать выполнение учебных задач в режиме реального времени»
и «возможность удалённого контроля учебного процесса».

## 19. Сквозной срез «ДДС: действия с карточками» — реализовано

Первое занятие, которое проходит целиком: вход → лобби → роли → карточки → статусы →
доклады бригады → итог. Режим ТЗ «действия с карточками» (§18.3): люди — ДДС,
оператор 112, заявитель и старший бригады — боты.

### 19.1 Как устроено

```
 web/arm.html (обучающийся)        web/teacher.html (преподаватель)
        │  WS: команды, события            │  REST: создать, роли, старт, стоп
        │  REST: вход, лобби               │  WS: монитор раз в секунду, итоги
        ▼                                  ▼
 server/app/main.py — FastAPI: REST, WebSocket, тикер 0,2 с, доставка по адресатам
        │  все обработчики async: движок однопоточный и живёт в цикле событий
        ▼
 server/domain/engine.py — движок занятий: очередь событий по серверным часам
        │                     (карточки по таймлайну, статусы ботов, доклады бригады)
        ├── lesson.py      лобби: состояния, роли, связь, видимость карточек
        ├── scenario.py    пакет сценариев + вид карточки у ДДС + полоса служб
        │     └── Router ──► libarm112 (ekp, C) или эталон — результат одинаков
        ├── arm112.reference.fsm   допустимые статусы
        └── evaluation.py  итог по 7 категориям памятки
```

Движок детерминирован и не знает о транспорте: наружу он только возвращает список
`(адресат, сообщение)`. Поэтому целое занятие проверяется тестом на поддельных часах
(`tests/test_engine.py`), а транспорт — отдельно, через HTTP и WebSocket
(`tests/test_api.py`, включая настоящий uvicorn с настоящим клиентом).

### 19.2 Сообщения

| Направление | Тип | Смысл |
|---|---|---|
| клиент → сервер | `hello` | первое сообщение: токен |
| клиент → сервер | `open_card` | карточка открыта — статус «Получена службой» (памятка) |
| клиент → сервер | `set_status` | статус, номер наряда, комментарий; `seq` — номер команды |
| сервер → клиент | `state` | снимок: занятие, карточки со статусами, `last_seq`, итог |
| сервер → клиент | `card`, `card_status` | новая карточка; новый статус любой службы и допустимые следующие |
| сервер → клиент | `call` | доклад старшего бригады (сейчас текстом) |
| сервер → клиент | `status_ack`, `status_rejected` | команда учтена (или повтор) / отклонена автоматом |
| сервер → клиент | `result` | итог занятия для участника |
| сервер → преподаватель | `monitor`, `results` | монитор занятия; итоги всех участников |

Эталон ответа (`expect`) и доклады бригады на рабочее место не уходят — это проверяет тест.

### 19.3 Пакет сценариев

`data/scenarios/dds_shchukino_v0.json` — 10 карточек для ДДС района Щукино. Эталоны взяты из
примеров нарушений памятки ДДС, где заказчик сам указал правильный статус и комментарий:
«Не принята» с указанием, куда передано (УК «ПИК», ООО «Практика», ОЭК), отказ от
выполнения с причиной, ход работ по докладам бригады. Пакет проверяется при загрузке
целиком: коды есть в классификаторе, карточка доходит до роли через маршрутизацию,
доклады бригады ведут по допустимым переходам, ссылки на другие карточки существуют.

### 19.4 Экран ДДС — по снимкам стенда

Размеры и цвета сняты со снимков стенда пипеткой (`UI-SPEC.md`, часть III): лента
с колонками стенда, карточка, полоса служб с переносом вверх, раскрытие истории статусов,
форма статуса с затемнением. Совпадает поведение, видимое на кадрах: после «Начало
реагирования» доступны «Прибытие», «Отказ от выполнения работ», «Работы завершены»
(sdds_14); номер наряда сохраняется между шагами, комментарий сбрасывается.

Комментарий к «Не принята» интерфейс **не требует** — как и боевая система, судя по тому,
что его отсутствие стоит в памятке нарушением №4. Тренажёр даёт ошибку совершить,
чтобы оценка её поймала.

Элементы тренажёра, которых нет в боевом АРМ, выделены иначе (тёмная полоса с жёлтой
линией, блок «доклады старшего бригады»): обучающийся не должен принять их за часть системы.

### 19.5 Что осталось заглушкой

| Что | Сейчас | Дальше |
|---|---|---|
| Вход | имя и роль, без пароля | учётные записи, RBAC (ТЗ) |
| Хранение | в памяти сервера; перезапуск сбрасывает занятия | PostgreSQL + `evlog` |
| Доклады бригады | текстом во всплывающем окне | голос: TTS и `rtpd` (§7, §6.10) |
| Признаки в карточке | формулировки классификатора | слой `ui_label ↔ код` (`UI-SPEC.md` §4.2) |
| Пакеты сценариев | один, написан вручную | генерация (§9) |
